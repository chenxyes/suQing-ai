## 复现

使用 Node 20 或 22 及现有依赖：

```sh
npm run check:behavior
node scripts/behavior_model_eval.mjs --dry-run
node scripts/behavior_model_eval.mjs --output /tmp/behavior-eval.json
# 可选：从指定只读 SQLite 获取聊天 provider 配置，仍在临时数据库回放
node scripts/behavior_model_eval.mjs --settings-db /path/to/settings.db --output /tmp/behavior-eval.json
```

支持 --variant on|off|both 与 --scenario support|celebrate|repair|ordinary。会真实调用模型并产生费用。脚本返回码只表示自动接线检查结果；人工逐句复核仍是必需步骤。

## 推荐的后续架构

用户追问是否有更好的方式后，推荐组合方案：先把已确认事实、未知信息、人物性格与本轮行动分开组织，再根据验证结果启用输出审查。不要仅在原提示后追加一个判断模型。

1. 事实与事件状态保留原话、说话人、时间、来源 ID、确认状态。向量搜索只返回候选；未回答的“自己煮还是买的”不能成为事实，过期或完成的约定不能继续跟进。复用既有记忆来源校验与独立 PR #8 的事件闭环，不再造一套记忆库。
2. 继续复用 Inner OS 的结构化判断，把本轮输入和有限证据分清。稳定人设可放在 SOUL.md 风格的文件中维护，每轮仅选当前相关的行动和事实；文件本身不会让模型永久记住，也不会自动免除上下文成本。
3. 回复生成后校验事实断言、约定、额外催促、停止边界与选定行动是否一致。审查必须看到原始证据，不能只看流畅的草稿；保留现有安全处理和人物口吻。证据不足应删除推断或表达不确定。
4. 先在隔离评测中审查全部测试样本，测误判、漏判、修订效果和完整调用成本，再决定哪些风险路径必审、哪些普通回应可跳过。不要一开始就靠几条关键词假定低风险，导致漏掉“买对了”一类断言。超时或失败时的回退策略也需验收。

审查会增加调用与延迟；不能继续声称所有行为轮只需两次模型调用。是否选择不同 provider/小模型、是否裁剪或重新生成，需要同一组固定失败样例验证，当前没有证据指定某个模型最优。

| 选项 | 优点 | 局限与当前建议 |
|---|---|---|
| 事实约束生成 + 经验证的按需输出审查 | 同时处理信息混淆和最终话语失控 | 最推荐；先在测试中测清额外开销与审查漏判，再灰度启用 |
| 仅加一个输出审查模型 | 接入快，便于暴露现有坏回复 | 可以作为测试阶段的第一步；同样会误判，不能替代事实/事件状态 |
| 仅重构提示，保持双调用 | 额外延迟小，上下文更清晰 | 必做基础，但本轮提示修订已证明不能单独提供稳定的结果保障 |
| 更换更强的聊天模型 | 可能快速改善指令遵循 | 应用固定样例做盲评；不能修复错误记忆、事件状态或缺少证据的问题 |
| 微调或偏好训练 | 可固化稳定表达风格 | 当前不优先；先有足够授权的优质数据和稳定评测，且动态记忆仍需工程处理 |

本节为建议设计，尚未实施。当前不自动进入 V2 或宣称 V1 产品效果验收完成。
