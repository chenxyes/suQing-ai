# 中转兼容与聊天、记忆问题排查（2026-09-18）

本文只保留汇总证据，不包含用户聊天、密钥或接口地址。服务器检查均为只读，没有修改生产配置。

## “走神”回复

`src/ai.mjs` 的 `generateReply` 在 `text` 为空时返回固定兜底，最终异常也返回同一句话。部署的四个核心文件与初始提交 `3de4e36` 一致（SHA-256 比对），排除了本地排查错版本的情况。

所查 `/app/logs/bot.log` 约 2 MB：45 条 `[ai] 回复:` 以兜底开始，0 条 `[ai] chat 错误`，1 条请求 abort 的 retry。`docker logs --since 72h` 未检出匹配错误，故依据容器内应用文件而非 Docker 日志缺失推断。

这表明多数症状不来自最终抛错路径。但不能据此证明上游 45 次都返回空内容：兜底被保存到对话历史后，模型也可能复述。旧实现丢弃 `finish_reason`、拒绝字段和响应类型，因此无法追溯空内容究竟来自思考 token 耗尽、过滤、协议差异或中转异常。禁止把尚无证据的上游原因说成已确认事实。

已确认的代码缺陷：空内容当成成功，不进入重试；无结构化诊断；SDK 默认重试与业务重试可能叠加；统一 30 秒 abort 不适合所有中转；固定兜底被写入上下文。修复方向是边界校验、分类有限重试、可配置有界超时、有效配置和结束原因诊断、阻断故障文本反馈循环。

有效聊天模型来自数据库设置：`deepseek/deepseek-chat`，环境中的 `deepseek-flash` 被覆盖。此差异不等于故障，但只观察 `.env` 会误判实际请求模型。

## 记忆（仅分析，暂不修复）

### 已证实的运行故障

默认 embedding provider 是 Gemini。API key 存在但含非 ASCII 字符，日志 193 次出现 ByteString 编码失败。没有读取或输出密钥值。`embedText` 失败返回 null，聊天召回随后使用关键词路径。

恢复 embedding 需要正确配置并验证服务。不能只换模型后继续比较旧向量：不同模型即使维度相同也不在同一语义空间，现有存储缺少模型版本标识。应在以后单独迁移索引、保留原文并分批重建，不能在这次端点配置功能中静默重算生产记忆。

### 代码层面的风险

- `extractAndSaveMemories` 对少于 8 字的输入直接退出，可能忽略生日、姓名或简短纠正。
- 提取输入同时包含用户内容和 AI 回复；仅用 prompt 区分事实来源，缺少逐条证据绑定。
- 关键词按空格/标点切分，连续中文句子常成为整串 `LIKE` 条件，而非实际关键词。
- 默认召回 7 条，关键词路径先拿最多 5 条 pinned；稳定旧信息可能挤占相关事件。
- 语义召回没有最小相似度门槛；即使整体不相关，也会按重要性补足结果。
- 主要召回 SQL 未限定 `memory_status='active'`，已归档/失效信息存在重新进入上下文的风险。
- `saveMemories` 直接插入，不能把 memory_v2 中的去重辅助函数存在视为主写入链已做矛盾消解。

以上不是对每个错记案例的归因：尚未拿具体事实纠正前后的消息、写入与召回记录逐项核验。

### 建议后续分阶段实施

1. 配置并测试 embedding；统计有效向量比例、模型/维度标识、失败和降级率。通过离线快照验证后重建索引。
2. 用带原消息 ID、主体、谓词、值、事件时间、生效区间和置信度的事实记录。纠正明确使旧事实失效，保留溯源。
3. 先检索 active 且相关的记忆；中文分词或混合检索；设置相似度门槛；给固定资料和事件分别预算。
4. 提取支持简短纠正，要求引用用户证据；模型自行补充的情节不作为用户事实。
5. 用“不喜欢/喜欢变化、昨天/今天、本人/朋友、否定与纠正、未提到就不编造”等样例离线评估，再考虑上线。
